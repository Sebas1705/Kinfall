# @kinfall/mobile

`apps/mobile` is an Expo (managed) app on Expo SDK 58 (React Native 0.88.1, React 19.3.0; the three are pinned to exact versions so device determinism checks are reproducible). It has no committed native folders: it runs in Expo Go for development, and `apps/mobile/android` and `apps/mobile/ios` are generated by `expo prebuild` and git-ignored. The app is **Kinfall** (`name` Kinfall, slug and scheme `kinfall`, application id and bundle id `es.sebas1705.kinfall`; see [ADR 0002](../../docs/adr/0002-kinfall-name-and-tester-distribution.md)); the npm package is `@kinfall/mobile`, and the storage keys keep the old `webgames.*` names so saves survive. Testers install a signed release build from Firebase App Distribution: [docs/distribution.md](../../docs/distribution.md).

It looks like a game, not a form: the "dusk-lit pixel fantasy" scene art of the shared core (`@kinfall/core/art/scene`, [style spec](../../docs/superpowers/specs/2026-11-20-visual-style-design.md)) is drawn with Skia, from the title hero to the battle stage, and every control and panel wears a pixel frame (see [Scene art](#scene-art)).

It opens on the **title screen** and plays a whole run by touch: pick a starter, keep or type a seed and choose **New run**. The map of the zone follows; a battle node (wild, elite, boss) opens the **battle screen**, and recruit offers, shrines, caches and mysteries open the **event screens**, until the **end screen** shows the result and score. Why the app shares a core with the web game: [ADR 0001](../../docs/adr/0001-shared-core-two-shells.md). It was built following the [React Native plan](../../docs/superpowers/plans/2026-11-16-react-native-app.md). What has not been verified on real devices: [Owner-only steps](../../docs/owner-steps.md).

## How to play a run

1. Start the app (see below). The title shows the three starters, **New run** and **Options** (the seed field, prefilled with a random 8-character seed, is in its sheet). **Continue run** is enabled only when a valid save exists.
2. Choose **New run**: the map of zone 1 shows the party, the souls and seven steps, step 1 at the top and the boss last. Available nodes have a solid border and say "available"; the others say "locked".
3. Tap an available node: the run saves. Step 1 nodes are battles: the battle screen shows the rival (HUD left, creature right), your creature (creature left, HUD right), the prompt and one button per choice. Tap a move: the turn is applied and saved first, then it plays (lunge, hit blink, HP bar tween, status chip pop, heal glow, swap and faint fades) while the choices stay disabled. When the battle ends, the next phase shows (the map, a recruit offer or the end of the run) with the run log lines of the battle's end.
4. Events: a won wild battle offers the creature (**Recruit** / **Let it go**; with a full party, one **Replace {species}** per member with its HP, and "Let it go" is the screen-reader focus on arrival). A shrine offers **Rest**, **Evolve {species}** (with its cost; disabled with "Not enough souls" in text when souls are short) and **Leave**; a cache **Take the cache**; a mystery **Open it** / **Leave it**. Each pick is saved and the map comes back with its log line.
5. The end screen says **Run won** or **Run lost** in text, then the score (core's `runScore`) and the stats. **New run** clears the save and starts at once from a fresh seed with the last starter of this session (the first starter after a resume, since a save does not record it); **Back to start** (or Android back, as the run is already over) clears the save and returns to the title.
6. Kill the app and open it again: **Continue run** resumes into the same battle (same HP, focus, status, rival intent and choices; the battle log starts empty), the same event, the same end screen or the same map.
7. To leave a run, use **Abandon run** in the Settings sheet (the HUD button) on the map or in battle, or Android back anywhere in the run (back opens the confirmation; a second back closes it). **Yes, abandon** deletes the save and returns to the title with a fresh seed.
8. The ES/EN toggle on the title switches every screen and is remembered. Next to it, **Reduce motion** stills the scene art and the battle animations on top of the system setting (also remembered).

## Structure and navigation

`apps/mobile/src`:

- `run/session.ts`: the run session, a plain object with no React, unit-tested on its own. It owns the current `RunState`, `start(seed, starterId)`, `resume()`, `abandon()`, `discardSave()`, `pickNode(nodeId)`, `act(action)` (any run action: battle turns and event choices) and `newRun(starterId?)` (the end screen's New run: clear, then start from a fresh seed), the cleared-node `trail` of this session (as the web controller keeps it), the run log (run events; lines come from core's `runEventLine` at render time, so a language change rebuilds them) and the save warning. Its immutable snapshot carries `view` (`map`, `battle`, `event` or `end`, from `runViewOf(phase)`), which is all the Run screen routes on. `run/useRunSession.tsx` has `RunSessionProvider` and `useRunSession()` (`useSyncExternalStore`).
  - Autosave: every applied action enqueues one write of the state it produced through core's `createAsyncRunStorage` (slot `webgames.run.v1`). Writes, and the clear of an abandon or a discard, run one at a time in enqueue order, so two quick taps never interleave and the last write holds the latest state. A failed save shows one dismissible banner per failure streak, a later good save hides it, and play goes on. A rejected action changes nothing, saves nothing and logs a warning.
- `navigation/AppNavigator.tsx`: one native stack with `@react-navigation/native` 7 and `@react-navigation/native-stack` (plus `react-native-screens` and `react-native-safe-area-context` at the versions `npx expo install` pins for SDK 58; all of them run in Expo Go). Routes: `Title` -> `Run`, where `Run` is one screen that draws every phase, so the stack never grows during a run, and the dev routes `Hello`, `Gallery` and `SelfTest`. Headers are off. Android back on the Run screen opens the abandon confirmation instead of leaving; on the title it exits the app. The title re-reads the save every time it gains focus.
- `screens/TitleScreen.tsx` is the title in the console layout (no page scroll): the hero (zone scene, chosen starter and the "Kinfall" wordmark image) over a strip of the three starters, each a 48dp radio card (the hint of the chosen one below the strip), **Continue run** and **New run** in the rail, and for a damaged save its notice and **Discard saved run** (its two-step confirmation opens in a sheet: it needs more room than the rail has). The HUD has **Options** (a sheet with the seed field, core's `seedFromRandom` and alphabet in `packages/core/src/platform/seed.ts` shared with the web title, fed by `platform/random.ts` (`globalThis.crypto.getRandomValues` when the engine has it, `expo-crypto` otherwise), the saves-live-on-this-device note and the **Dev tools** link, which exists only in development bundles) and **Settings** (language, motion, text size). The storage-unavailable notice sits in the rail. Sizes: `titleMetrics.ts`.
- `screens/MapView.tsx` draws core's `buildMapModel` as a fixed board in the primary region: one column per layer (step 1 first, the boss last; at most 7 columns of at most 3 nodes), each node a 48dp framed button with its pixel icon (one silhouette per type, dimmed when locked) and, under it, the short type name as real text (the first word of the label; fixed size, since the columns are 48 to 64dp wide). The state is not colour alone: locked nodes are flat, cleared ones carry a check, the current one a dot and the plate; `map.nodeLabel` is the accessible name. The rail shows the full name and state of the focused node and a legend. The HUD has the zone, the party chips, **Run** (a sheet with the party details and the run log) and **Settings** (with **Abandon run**, whose confirmation replaces the button there). Sizes: `mapMetrics.ts`.
- `screens/RunScreen.tsx` draws the snapshot's `view`: the map, the battle, or `PHASE_VIEWS[view]` for event (`EventView`) and end (`EndView`); each draws its own console screen, and the route hands it the save banner (above the content), the seed line and the abandon confirmation (both in the Settings sheet, see `ui/useRunSheets.tsx`) and the scroll handle of the fallback layout. The run log is one message line (the newest lines, a polite live region outside the part a sheet hides; `RunLogMessage`) and the full list is in the sheets. A battle's final turn moves the run on at once (it is applied and saved before it plays), so the Run screen keeps the battle up until that turn has played and the turn controller calls `onEnd`; then it routes on the new phase. Every new phase starts scrolled to the top (in the fallback layout, where the primary region scrolls). Event and end screens have no abandon button, like the web; Android back still asks on an event (opening the Settings sheet with the confirmation), and on the end screen it goes straight to the title.
- `screens/BattleView.tsx` is the battle screen (see below).
- `screens/EventView.tsx` draws core's `buildEventModel` for recruit, shrine, cache and mystery in the console layout: the heading in the HUD, the vignette (when there is room) beside the description, the offered creature (sprite, name, elements and HP as text) and the full-party note in the primary region, and the choices as the rail (a column in landscape, in a rail wider than the contract's; two columns in portrait). Choices are exactly core's legal run actions (`legalRunActions`) plus evolve entries that stay listed but disabled, with the cost and "Not enough souls" in text. Each choice is a 48dp button whose accessibility label is its label plus its detail. The party details and the run log are in the **Run** sheet. Sizes: `eventMetrics.ts`. Screen-reader focus goes to the model's initial choice on arrival.
- `screens/EndView.tsx` draws core's `buildEndModel` in the console layout: the result as the HUD heading in text, the scene and the main score (one accessible element, "Score: 4540") in the primary region, **New run** and **Back to start** in the rail, and the detailed stats (each one accessible element, "Zones cleared: 3") and the run log in the **Run** sheet. One tap wins: a double tap never starts two runs. Screen-reader focus starts at the result. Sizes: `endMetrics.ts`.
- `dev/sampleRuns.ts`: `sampleRun(kind, content)` builds valid runs (they pass core's `validateRun`) standing on each event (`recruit`, `recruitFull`, `shrine`, `shrinePoor`, `cache`, `mystery`) on both endings (`won`, `lost`) and on the first battle of zone 2 or 3 (`battleZone2`, `battleZone3`), from a seed's own maps; no content or engine change. The tests use them, and the hello screen's **Save sample run** buttons write one into the save slot so **Continue run** opens that screen on a device.
- `ui/`: `Button` (in a pixel frame), `PixelFrame` (`Plate`, `FramePressable`, `FrameBackground`), `PixelBar`, `MotionToggle`, `ConfirmPanel` (inline two-step confirmations, no system alert; shown where the button that opened it was), `LangToggle`, `PartyPanel`, `RunLogPanel` (`RunLogMessage` and the sheet's list), `SaveBanner`, `Hud`, `Sheet`, `SettingsSheet`, `useRunSheets` and `Screen` (the console shell inside the safe area: fixed regions without a page scroll when the window fits the screen's budget, and a pinned HUD and rail with a scrolling primary region when it does not; see [Accessibility and layout](#accessibility-and-layout)). `theme.ts` mirrors the web tokens for light and dark, which follow the scene art's UI palettes (parchment and dusk; including surface, accent, focus and danger, an `outline` for unfilled controls and the `plate` and `button` bodies of the frames), exports `TOUCH` (48dp) and lists every colour pair with its WCAG minimum (`CONTRAST_PAIRS`, checked by a test). `platform/LangContext.tsx` re-renders every screen after a language change.

## Battle screen

- **One turn state machine for both apps.** The turn controller (`packages/core/src/models/battleController.ts`, moved from `apps/web/src/view/controller.ts` with its tests) is platform-neutral: it takes the UI, the scene, the timers and the logger as interfaces (`BattleUi`, `BattleScene`, `TimerApi`, `Logger`). It commits the new state before any animation, ignores input while a play is pending, settles each turn exactly once (normal end, rejection, throw or the watchdog `watchdogMs(eventCount)` = max(2500, 700 per event) ms), calls `onEnd` once after the final play settled, and rebuilds the texts once when the language changes during a pending turn. The web keeps thin re-exports (`apps/web/src/view/controller.ts`, `runTurn.ts`), so its code and e2e tests are unchanged. `packages/core/src/models/battleTurn.ts` (`splitBattleStep`, `battleTurn`) splits an applied run step into the battle events to play and the run events to log.
- `battle/useBattleController.ts` (`useBattleTurns`) wires that controller to React state (busy flag, choices from core's `buildMenu`, the battle log from `logLines`, a focus request) and sends each turn through the run session's `act({ type: 'battle', action })`, so the run is updated and autosaved before the turn plays. A rejected action is a no-op with a logged warning; the battle keeps its state. The screen opens from the run's saved `BattleState`, so a resumed battle shows exactly the saved HP, focus, status, intent and choices with an empty log.
- `battle/useBattleScene.ts` implements `BattleScene` with React Native's built-in `Animated`: attacker lunge, hit shake, HP tween, status chip pop (spring), swap fade out/in and faint fade. The creatures' values (position, opacity) run on the JS driver because the Skia stage reads them on its own frame clock; the HP bars (`scaleX` fills) and status chips stay on the native driver. Each event is also handed to an effect hook as it starts (`onEvent`), which starts the stage's decorative effects (see [Scene art](#scene-art)); the hook never delays the play. `battle/sceneModel.ts` is the pure part: what each side shows as the turn's events arrive. Every step has a hard time budget (nominal length + 150 ms, then a timer finishes it), a new render cancels a running play, and with reduced motion (the system setting, which on Android follows "Remove animations", or the app's own switch; `platform/motionSetting.ts`) nothing animates, the settled state shows at once and the effects show their still variants. The animation never changes the sim state.
- Layout, vertical-first and one-handed: node heading, the rival's HUD plate, the battle stage (edge to edge on phones), your HUD plate, the prompt and the choices (moves first, then swaps as "Swap to {species}"), **Abandon run** (the same two-step inline confirmation as the map, also from Android back), then the battle log last so a growing log never moves the buttons. Choices are 48dp buttons that name the move, its element (icon plus text), power and focus cost (`battle.power`, the only new string); disabled while a turn plays. HP and focus are written as text next to their bars; status is a text chip; the telegraphed rival move ("Next: {move}") is a text line in the rival HUD. Each HUD is one accessible element read as the web's `hud.summary`. Only the latest turn's lines sit in a polite live region, and after each settled turn screen-reader focus moves to the prompt above the choices (`AccessibilityInfo.sendAccessibilityEvent(..., 'focus')`), unless the abandon confirmation is open. When large text or a short window would push the choices below the creatures, the battle switches to its compact layout (a shorter stage, HP and focus on one line, the choices and **Abandon run** pinned at the bottom); on tablets, foldables and landscape phones the scene and the choices sit side by side (see [Accessibility and layout](#accessibility-and-layout)).
- Tests (`__tests__/screens/BattleView.test.tsx`, `__tests__/battle/*`, Jest fake timers and a mocked `Animated.timing`/`spring` from `test-support/battleFixtures.ts`): a whole battle with the real engine (one autosave per turn, choices locked while pending, the next phase with the end lines), `onEnd` exactly once, the watchdog and step budgets, reduce motion, a rejected turn, resume mid-battle, abandon by button and by back, a language change during a pending turn, labels and roles, focus.

## Scene art

The mobile half of the "dusk-lit pixel fantasy" style (phase C; the web half is in `apps/web/src/art`). Everything is drawn from the shared core's data (`@kinfall/core/art/scene`, contract in section 11 of the [style spec](../../docs/superpowers/specs/2026-11-20-visual-style-design.md)); the generators are not changed here.

- **One Skia canvas per scene** (`src/art/ArtScene.tsx`): the zone backdrop (`sceneForZone`, cached per zone and run seed in `art/sceneCache.ts`) with camera sway and cloud drift, ambient life (`prepareAmbient` / `sampleAmbient`), the platforms and shadows, the creatures at the `STAGE` anchors (the player mirrored) and the effects. Each frame is recorded into a Skia picture in device pixels and handed to one native `SkiaPictureView`; only that view re-renders per frame. Every pixel grid is baked once into a nearest-neighbour image (`art/skia.ts`, cached per grid), every scale is a whole number of device pixels per art pixel, and `androidWarmup` stays on for every canvas (the first-draw blank fix).
- **Framing** (`art/stageLayout.ts`, pure): boxes narrower than 560dp (phones) show the creatures' middle (x 46..212) as large as the width allows and crop 26 sky rows; wider boxes show the whole scene; a height cap (42% of the window stacked, 28% in the compact battle, 50% in two panes) wins over both, and the tiled layers then extend sideways. The compact battle lists both HUD plates first and crops its stage to a band from row 50 (the creatures and their platforms).
- **One clock** (`art/frameLoop.ts`): `requestAnimationFrame`, at most 30 fps while only ambient life moves, every display frame while effects or a turn play, and nothing while the app is in the background (`AppState`) or the navigation screen is blurred. With reduced motion a scene draws one still frame (and the still variants of effects for their short hold), then stops.
- **Battle** (`art/BattleStage.tsx`, `screens/BattleView.tsx`): the turn animator's events start the effects through `art/stageDirector.ts` (`effectsForBattleEvent`, then `prepareEffect` / `sampleEffect` per frame; the bookkeeping in `art/fx.ts` mirrors the web's `apps/web/src/art/fx.ts`: particle cap 112 - 32, hit flashes at most one per 500 ms, faints as particles only, the victory / defeat title held). Hit flash, tint, knockback, screen shake (at most 3 art px), element effects, heal, faint, super effective / resisted, miss, victory and defeat play on the stage; damage, heal and soul numbers float as outlined text (at least 16dp). Effects never lengthen a turn: they run on the scene clock and may outlive it. If drawing a frame takes longer than 24 ms several times in a row, the ambient life is dropped first.
- **HUD and controls** (`ui/PixelFrame.tsx`, `ui/PixelBar.tsx`, `ui/frames.ts`): plates and buttons are React Native views with the core's nine-slice frames (`plateFrame`, `buttonFrame`) drawn behind them in one small Skia picture each, at whole device pixels per cell (about 2dp); the frame's body colour is also the view's background, so text has its contrast pair before the picture draws. Buttons are raised, sink when pressed, go flat when disabled, and get the focus frame outside their box on keyboard / D-pad focus. The main action and the selected item (starter, language, current map node) wear the ornate plate. Bars are plain views at frame cells (`barStyle`: track, fill, shine, HP ticks every 25%). Light mode uses the parchment frames, dark mode the dusk frames; the gems take the run's zone accent. All text is real `Text` with the existing roles, labels, states and live regions.
- **Screens**: the title hero (zone 0 at dusk with the chosen starter and an unknown foe's silhouette) with the KINFALL wordmark as the image "Kinfall" (`app.title`); the map's zone banner, pixel node icons (dimmed when locked) and a dotted path with step markers; the event vignettes (shrine, cache, mystery, recruit camp) in a plate; the end scene with the victory or defeat flourish. The page palette in `src/theme.ts` follows the UI palettes (parchment light, dusk dark).
- **Accessibility**: every canvas, frame, bar and icon is hidden (`importantForAccessibility="no-hide-descendants"`, `accessibilityElementsHidden`) and never touchable; everything it shows is also text (names, HP, the battle log, node labels, event text). The only labelled art is the logo. Reduced motion is the system setting OR the app's **Reduce motion** switch (`platform/motionSetting.ts`, AsyncStorage `webgames.reduceMotion`): no sway, drift, shake, flashes or moving particles, a few frozen ambient particles, still effect frames.
- **Measuring**: build the bundle with `EXPO_PUBLIC_ART_STATS=1` (for example `EXPO_PUBLIC_ART_STATS=1 npx expo start --no-dev --minify`) and every scene logs `[art] <scene> fps=.. busyFps=.. draw=..ms max=..ms` every 5 s (`adb logcat -s ReactNativeJS`); off by default.
- **QA**: the dev tools' **Save sample run** also has `battleZone2` and `battleZone3` (a battle in the later zones), so each zone's stage can be checked without playing up to it.

## Accessibility and layout

- **Console layout**: every run screen uses core's pure layout contract (`@kinfall/core/layout/spec`, shared with the web): width classes at 600 and 840dp, height classes at 480 and 900dp, and the regions of each screen (HUD, primary, actions rail beside it in landscape or band below it in portrait). While the window fits the screen's budget (height divided by the effective text scale, the system font scale times the app's own text size) nothing scrolls; otherwise (200% text, tiny windows) the HUD and the rail stay pinned and only the primary region scrolls. Jest cannot measure a layout, so each screen's sizes are bounded and shared with its tests (`screens/*Metrics.ts`, proved by arithmetic in `__tests__/screens/runMetrics.test.ts` and `battleMetrics.test.ts` for 640x360, 914x411, 360x640 and 411x914 at text 100% and 130%). The app is not locked to portrait (`app.json` `orientation: default`).
- **Edge to edge**: content stays clear of the status bar, navigation bar and display cutouts through the safe-area insets; the status bar icons follow the theme.
- **Screen readers**: every touchable has a role (button, radio, link), a name and its state (disabled, checked, selected); map nodes read core's `map.nodeLabel`; sprites, element icons and bars are hidden; new log lines sit in polite live regions on Android and are announced once through `AccessibilityInfo.announceForAccessibility` on iOS (`platform/announce.ts`, keyed so a re-render or a language change never repeats them).
- **Motion**: battle animations, screen transitions and the scene art's movement are off with the system reduce motion / remove animations setting or the app's own **Reduce motion** switch in the Settings sheet (the scenes then stay still, with a few frozen particles).
- The checklist of what was verified, and what could not be, is in [apps/mobile/ACCESSIBILITY.md](ACCESSIBILITY.md).

## Dev tools, adapters and sprites

The dev tools keep the earlier screens. **Hello core**: type a seed (default `golden-0`), press **Run**, and it plays a whole run with the core bot and the first starter, then shows the starter, `hashRun` of the final state, the result, the score and the number of steps. For the same seed the hash must equal the one Node computes (for example `golden-0` gives `280338e8c541b53c`, the same as `run.golden.json`). Its **Damage saved run** button writes text that fails validation into the run slot, to try the title's damaged-save notice on a device, and its **Save sample run** buttons write a valid run standing on an event or an end (see `dev/sampleRuns.ts`), to reach those screens without playing up to them.

Platform adapters live in `apps/mobile/src/platform/`: `asyncStorage.ts` (`defaultAsyncStorage()`, `@react-native-async-storage/async-storage` as core's `AsyncStorageLike`, null if unusable), `mobileI18n.ts` (`installMobileI18n()` reads the saved language `webgames.lang` first, then configures core i18n with a synchronous in-memory adapter that writes through to AsyncStorage; the device language comes from `expo-localization`; `App.tsx` renders nothing until it resolves, so there is no flash of the wrong language) and `a11ySettings.ts` (`useA11ySettings()`: system reduce motion and font scale). The hello screen also has an ES/EN toggle, **Save last run** / **Load** buttons (none, ok with hash, corrupt, unavailable) and a read-only reduce motion and font scale line.

Sprites: `apps/mobile/src/art/` has `<CreatureSprite species scale />` and `<ElementIcon element scale />`. They draw the core generator's grid (`generateCreature`, `elementIcon`) with `@shopify/react-native-skia` (2.14.0, the version Expo SDK 58 pins; it ships inside Expo Go, so no development build is needed). Core's pure `gridToRects(grid)` (`packages/core/src/art/gridToRects.ts`) merges same-colour horizontal runs into rects, one Skia `Rect` each, with whole-pixel edges and anti-aliasing off so cells stay crisp at integer scales. Sprites are decorative (hidden from screen readers unless `accessibilityLabel` is passed) and the grid is generated once per species. Canvases set Skia's `androidWarmup`, which also paints the picture as a plain bitmap: without it the Android emulator now and then left one sprite blank on first draw (about 1 launch in 4; none in 8 launches with it). A dev **Gallery** screen (button on the hello screen) lists every species with its elements at scales 2, 3 and 4. Jest loads Skia through `@shopify/react-native-skia/jestSetup` (see `jest.setup.js`) and transforms it via `transformIgnorePatterns`.

## Run it

To run it on an Android emulator (paths are this machine's, adjust them):

```sh
export JAVA_HOME="$HOME/.jdks/jdk-21.0.12.1+1"
export ANDROID_HOME="$HOME/Android/sdk"   # the SDK that has emulator/ and platform-tools/
export PATH="$ANDROID_HOME/platform-tools:$PATH"
"$ANDROID_HOME/emulator/emulator" -avd <your_avd> &   # an API 34+ AVD
cd apps/mobile && npx expo start --android
```

The Expo CLI downloads and installs the matching Expo Go on the emulator the first time, then opens the app. No account, EAS or signing is needed. To use a phone, install Expo Go and scan the QR code that `npx expo start` prints (same network).

Metro uses Expo's default config (`apps/mobile/metro.config.js`): since SDK 52 it detects the npm workspace and watches the repository root, and package `exports` are enabled by default, so `@kinfall/core/<path>` resolves to `packages/core/src/<path>.ts` without aliases. `apps/mobile/tsconfig.json` extends `expo/tsconfig.base` with `strict` and `noUncheckedIndexedAccess` and type-checks the core modules the app imports.

## Device self test (determinism on Hermes)

The core guarantee is that the same seed gives the same battle and run on every engine. Jest runs on Node, so only the device can prove it for Hermes. The dev **Self test** screen (button on the hello screen) replays every entry of both golden files, `packages/core/tests/golden/battle.golden.json` and `run.golden.json`, on the device JS engine. The screen imports those files directly (Metro bundles JSON from the watched repository root), so there is no copy that could drift.

- The runner is core's pure `runGoldenSelfTest` (`packages/core/src/sim/selfTest.ts`, with `checkBattleGolden`, `checkRunGolden`, `combineSelfTest` and `selfTestSummary`). It makes the same calls and comparisons as the Node golden tests: battle final hash and winner; run final hash, result, score and tags, with no rejected actions. Each file must have a minimum number of entries (3 battles, 4 runs) and every entry needs non-empty actions. Malformed input gives `ok: false`, never an exception.
- It runs only when you press **Run self test**. It yields to the UI between the two files so the spinner shows. The screen shows a large **PASS** or **FAIL**, the battle and run counts, the elapsed time, the first mismatch with its expected and actual values, one line per entry, a monospace summary, and the engine: `HermesInternal` presence and version, platform and OS version, React Native version, Expo SDK, device model (Android `Platform.constants`) and `typeof structuredClone`.
- It also logs two lines that start with `[selftest]` (summary with elapsed time, then the engine). You can read them without the UI: `adb logcat -d -s ReactNativeJS | grep selftest`.
- Auto-run is off by default. It turns on when the bundle is built with `EXPO_PUBLIC_SELFTEST_AUTORUN=1`, or when the app is opened with a URL that has a `selftest` path segment or a `?selftest=1` query, for example `exp://127.0.0.1:8081/--/selftest` in Expo Go or `kinfall://selftest` in a build (release builds included: the self test only reads the bundled golden files) (`app.json` sets the scheme).

Run it on the Android emulator (environment as above):

```sh
"$ANDROID_HOME/emulator/emulator" -avd <your_avd> -no-snapshot &
adb wait-for-device
cd apps/mobile && npx expo start --android    # then: Dev tools > Self test > Run self test
# or without touching the UI: open the app on the self test, it runs on mount
adb reverse tcp:8081 tcp:8081
adb shell am start -a android.intent.action.VIEW -d "exp://127.0.0.1:8081/--/selftest" host.exp.exponent
adb logcat -d -s ReactNativeJS | grep selftest
# or bake auto-run into the bundle (also a good check of the minified production bundle)
EXPO_PUBLIC_SELFTEST_AUTORUN=1 npx expo start --no-dev --minify
```

A pass looks like `[selftest] PASS battle 3/3 run 6/6 elapsed=39ms (battle 6ms, run 33ms)`. A failure looks like `FAIL battle 2/3 run 6/6 first=battle#1 {"expected":{...},"actual":{...}}`. A failure on a device is a determinism bug in core. Do not update the goldens to hide it.

### Verify on a real phone

This is an owner step. It needs a physical device and cannot be done from CI.

1. Install **Expo Go** from the Play Store (or the App Store). It must support SDK 58.
2. Over Wi-Fi: put the phone and the computer on the same network, run `cd apps/mobile && npx expo start`, and scan the QR code (Android: from Expo Go; iOS: with the Camera app). If the network blocks it, try `npx expo start --tunnel`.
3. Or over USB (Android): turn on Developer options and USB debugging, connect the phone, accept the debugging prompt, then run `adb devices` (the phone must be listed), `adb reverse tcp:8081 tcp:8081` and `npx expo start --android`.
4. In the app, press **Dev tools** (at the bottom of the title screen), **Self test**, then **Run self test**. Check for **PASS**, `Battle 3/3`, `Run 6/6` (or the current golden counts) and `HermesInternal: present`. Write down the Hermes version, the device model and the elapsed time.
5. If the result is **FAIL**, keep the screen (screenshot) or the `[selftest]` lines from `adb logcat -d -s ReactNativeJS` and report the first mismatch.

## Mobile tests

**Jest** (Node, no device): `npm run test:mobile` from the root, or `npx jest` inside `apps/mobile`. Pass a path to run one suite (`npx jest __tests__/ui/Screen.test.tsx`) and `--coverage` for a per-file report. The scene art has its own suites (`__tests__/art/*` for the framing, the frame clock and the effect bookkeeping, `__tests__/ui/PixelFrame.test.tsx` for the frames and their contrast, `__tests__/platform/motionSetting.test.tsx` for the reduce-motion switch and `__tests__/screens/Art.test.tsx` for the hidden canvases on every screen); under Jest Skia has no native side, so the canvases render empty and the tests check structure, labels and timing, not pixels. Shared helpers live in `apps/mobile/test-support/`: memory storages and seeded sessions (`runFixtures.ts`), instant animations and a promise flush (`battleFixtures.ts`), a real double tap (`press.ts`). `__tests__/smokePath.test.tsx` plays the same taps as the Maestro smoke flow below on the whole app, so a change that breaks the flow's assumptions (seed `SMOKE002`: a wild battle won in one turn, then a recruit) fails in Jest first.

**Maestro** (device end-to-end): two flows in `apps/mobile/.maestro/`, which find every element by its `testID` (the Android resource id), so they work in both languages.

- `smoke-run.yaml`: new run with seed `SMOKE002`, the first node, the battle, the recruit, the map, abandon with confirmation, back on the title with no save.
- `resume-after-kill.yaml`: saves the dev-tools `recruit` sample, kills the app process (`killApp`, like `adb shell am kill`), relaunches and checks that **Continue** opens the recruit screen.

They target a debug build of package `es.sebas1705.kinfall` (the Dev tools link only exists in debug builds), not Expo Go. To run them on an emulator, with [Maestro](https://docs.maestro.dev) installed:

```sh
cd apps/mobile
npx expo prebuild --platform android --no-install   # generates android/ (git-ignored); revert the "android" script it rewrites in package.json
npx expo run:android                                # builds and installs the debug app, starts Metro
maestro test .maestro                               # both flows; or: maestro test .maestro/smoke-run.yaml
```

The flows were checked against the Maestro docs and parsed as YAML, but they have **not** been run yet: Maestro is not installed on the development machine. The first device run is an owner step.
